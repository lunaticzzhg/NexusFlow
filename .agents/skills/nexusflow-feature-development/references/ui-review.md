# App/KMP Compose UI Review

用于审查 NexusFlow App/KMP 的 Compose 页面、组件、底部面板、导航表面和 UI 改造。它定义评审方法，不定义新的视觉风格、组件库或全局抽象。

## 目标

让 UI Review 基于可复用的判断标准，而不是临时的审美意见。Review 同时检查用户可用性、布局韧性、视觉一致性、状态完整性、Compose 实现边界与实际渲染结果。

后端协议、权限和持久业务事实仍优先于客户端推断；本参考不允许前端自行创造业务状态或可执行动作。

## 触发

在以下情况读取本参考：

- 新页面、页面改造、关键组件或底部面板评审；
- 用户反馈“页面不对”“布局不稳”“看起来不一致”或“帮我 review UI”；
- Figma 或静态设计稿被翻译为 Compose 布局；
- 检查长文案、小屏、键盘、安全区、加载/空/错误状态或提交体验；
- 审视一组 UI diff 的一致性、可用性与复用边界。

轻量改动可只检查受影响部分；页面级改造按完整流程执行。

## Review 流程

### 1. 先冻结标准

在列问题或给修改建议前，写清：

- 页面目标：用户在此页面要完成什么；
- 主操作：最重要的下一步是什么，是否在合理触达位置；
- 页面模型：列表、详情、表单、对话、选择、编辑、沉浸内容或其他；
- 信息层级：标题、关键内容、状态、说明和次要操作的优先顺序；
- 视觉依据：现有 `MaterialTheme`、`OrbitSpacing`、形状和图标规则，或明确的 Figma 视觉事实；
- 完成标准：要验证的状态、设备尺寸与关键交互。

若存在多个合理页面模型，先列出选项并选定一个；不要通过连续调 padding、`Spacer` 或动画来试出页面模型。

### 2. 按层评审

按以下顺序检查。前一层不稳定时，不进入下一层的视觉微调：

1. 任务清晰度与信息层级；
2. 内容区块、布局结构、滚动与固定区域；
3. 对齐、间距节奏、留白和触达面积；
4. 颜色、文字、视觉权重与组件克制；
5. 反馈、状态与微交互。

同一个问题连续两次局部修正仍不正确时，停止追加微调；重新确认页面模型、对照现有成熟实现，或更换布局策略。

### 3. 区分代码审查和渲染验收

代码审查覆盖：状态所有权、组件边界、token 使用、约束模型、可访问性语义、测试和共享组件复用。

渲染验收覆盖：实际间距、对齐、尺寸、视觉平衡、溢出、触控舒适度、键盘与安全区表现。未在 preview、模拟器、浏览器或设备中检查时，不得宣称视觉已验证或与设计已对齐。

## Review 维度

### 任务与可用性

- 用户能否在数秒内理解页面当前状态和主要下一步？
- 主操作是否明显、可触达，且不与低优先级或危险操作竞争？
- 危险、不可逆和次要操作是否处在正确层级，并有必要确认？
- 触控目标是否至少满足 `MaterialTheme.orbitSpacing.minimumTouchTarget`？
- 用户可见文案、`contentDescription`、空态和错误态是否来自 Compose Resources？

### 信息层级与视觉系统

- 标题、关键数据、状态、说明、操作是否有明确的视觉优先级？
- 颜色是否承担语义，而非被当作普通装饰；警告/错误色是否只用于相应语义？
- 页面是否从 `MaterialTheme.colorScheme`、`MaterialTheme.typography`、`MaterialTheme.shapes` 和 `MaterialTheme.orbitSpacing` 取视觉规格？
- 是否避免业务页面中的裸颜色、零散 dp、圆角、阴影和重复的局部组件样式？
- 图标是否表达正确语义、由 `Res.drawable` 加载并由调用侧 tint，而非在页面中嵌入 SVG path 或硬编码产品色？

### 布局与韧性

每个显著区域先识别其真实约束，再判断实现是否合理：

| 类型 | 适用区域 | Compose 实现方向 |
| --- | --- | --- |
| 填满父容器 | 卡片、输入框、按钮、列表行、选择背景 | 父级 padding 后 `fillMaxWidth()` |
| 均分/分配 | Tab、等宽操作、重复列 | 固定 gap + `weight` 或明确列模型 |
| 内容驱动 | 文本、badge、短标签、行内操作 | 自然尺寸 + 父级最大边界 |
| 固定契约 | 图标、触控区、按钮高度、媒体比例、边框 | 命名尺寸；只固定真实控件契约 |
| 装饰层 | 背景、渐变、遮罩、浮层 | 不参与内容区宽高计算 |
| 设计稿样本 | 文本框、导出小数、临时 group 尺寸 | 不直接成为 Compose 约束 |

重点检查：

- 不把“父容器宽度减左右边距”写成固定宽度或无依据的最大宽度；
- 不用静态设计稿的文本宽高锁死标题、描述和 badge；
- `maxWidth` 只作为阅读宽度或内容上限，不是固定宽度的替代写法；
- 明确额外高度归属：滚动内容、固定页头、固定页脚、导航栏、安全区或键盘区；
- 列表保持稳定的 leading / content / trailing 区域，不以临时缩小文字解决挤压；
- 检查小屏、长中英文、无空格长字符串、字体缩放、横向尺寸、window inset 和键盘弹起。

### 状态与反馈

- 每个异步页面或内容区域是否有 loading、content、empty、error 和提交中状态？
- 初始请求失败时，是否显示错误而不是错误的空态？
- 刷新时是否保留已有内容，而不是不必要地全屏阻塞？
- 可恢复的数据加载失败是否有可见重试入口？
- 长任务是否展示进度或状态，而不是无限 spinner？
- 每个可点击动作是否有明确执行 owner、成功结果、失败反馈和不可用策略；缺少正式合同的动作是否隐藏、禁用或标明为非交付占位，而不是空实现？
- 提交中是否阻止重复触发、误返回、误关闭或与同一区域的冲突交互？
- 输入框、按钮、Tab、卡片和 Sheet 是否检查默认、选中、按下、禁用、加载、聚焦、错误和长文本状态？
- 是否显式检查 Material 3 的默认 focus/error border、ripple、elevation、minimum size 和 overlay 没有造成视觉漂移？

### Compose 实现边界

- Screen 是否只负责收集 `UiState`、派发 Intent、消费 Effect、导航与页面编排？
- Content 和子组件是否只接收所需 UI 数据、`Modifier` 与语义化回调，而非 ViewModel、Repository、NavController 或整个 `UiState`？
- 是否避免把 `UiState` 复制到 `remember`，或在 composition 中发请求/写业务状态？
- 是否优先复用现有组件；只有第二个真实消费者或稳定跨页面结构才提取到 `core`？
- 文件增长是否按完整视觉区块拆分，而不是机械移动零碎函数？

## 验证

按风险选择最窄有效检查：

- 关键点击、状态分支和无障碍语义：Compose UI 测试；
- Figma 或固定布局风险：验证关系而非单一像素，例如紧凑宽度下两侧边距仍成立、均分项可容纳、文本不裁切；
- 修改后按 `verification.md` 运行对应 App/KMP 测试或编译；修改 App Kotlin/Gradle 时运行 `./gradlew :app:composeApp:ktlintCheck`；
- 关键页面尽可能在 preview、模拟器或设备中检查首屏、加载、空、错、提交中、长文案、小屏和键盘状态。

优先报告会阻塞任务、造成误操作、状态误导、布局溢出或跨屏失效的问题；不要把纯个人偏好包装成缺陷。

## 边界

- 本参考不引入 Oren 的色板、Flutter 组件、底部面板 API 或视觉风格；NexusFlow App 继续以自身 MaterialTheme 和 Compose Resources 为准。
- 不因一次 Review 新增全局 token、共享 Sheet 框架或组件库；出现真实重复消费者后再评估提取。
- API、权限、持久业务状态、导航合法性和上下文身份边界仍遵循 NexusFlow architecture authorities 与 feature-development 专题参考。
