# Orbit MVP 需求文档

## 1. 产品定义

**Orbit** 是一个可审批的个性化休闲日程 Agent。它主动汇集赛事、电影和本地活动等机会，结合用户偏好与现实约束生成有亮点、可执行的候选计划；只有用户明确批准后，系统才会创建日历事件或提醒。

产品不以“替用户追踪所有资讯”为目标，而是帮助用户**不用持续刷动态，也不错过真正适合自己的安排**。

### 1.1 MVP 成功标准

用户可以在 Android App 中完成以下单一闭环：

1. 填写或修改个人偏好。
2. 发起“帮我安排本周末”任务，并可补充自然语言要求。
3. 收到 2–3 个符合时间、预算和兴趣约束的候选计划。
4. 查看每个计划的推荐理由、数据来源与待执行动作。
5. 编辑、批准或拒绝创建日历/提醒的操作。
6. 在任务时间线查看规划、校验、审批、执行和失败重试结果。

本地演示阶段使用内置模拟数据源；不得因外部 API 不稳定而阻塞完整流程。

## 2. 用户与使用场景

### 2.1 目标用户

- 有多种休闲兴趣、但没有时间持续追踪赛事、电影和城市活动的城市用户。
- 需要在预算、通勤、作息和已有日程之间做取舍的用户。
- 希望保留最终决定权，不接受未经确认的日历写入或通知轰炸的用户。

### 2.2 核心场景

**场景 A：周末主动编排**

用户说：“这周末安排一下，想看利物浦比赛，预算 300，周日下午不要占用。”

系统检索用户偏好、空闲时间和模拟的赛事/电影数据，返回 Plan A/B/C。用户批准其中一个计划后，系统创建日历事件与赛前提醒。

**场景 B：偏好驱动的惊喜候选**

用户设置“英超优先、喜欢悬疑片、通勤 30 分钟以内、每周最多一次新体验”。系统在满足硬性约束的情况下，额外提供一项可跳过的“惊喜活动”。

**场景 C：中断后恢复**

用户在审批页退出 App 或网络中断。重新打开 App 后，仍可看到同一待审批任务；重复批准不会创建重复事件。

## 3. 范围与边界

### 3.1 MVP 内

- 个人偏好档案：兴趣、优先级、预算、通勤、时间禁区、惊喜偏好。
- 内置模拟插件：英超赛事、电影场次、日历、通知。
- 自然语言任务输入与结构化候选计划生成。
- 时间、预算和偏好规则校验。
- 创建日历事件与通知提醒前的可编辑审批。
- 任务状态机、任务时间线、失败展示和安全重试。
- 本地缓存与任务列表恢复。

### 3.2 MVP 外

- 真实购票、订位、支付或自动发布内容。
- 真实抖音账号接入与自动发布。
- 社交拼团、多人共同编辑日程。
- 金融交易、荐股或自动打新。后续金融模块仅能提供可溯源的信息与提醒。
- iOS 正式发布；保留 KMP/iOS 工程边界，但 Android 优先交付。

## 4. 功能需求

### FR-01 偏好档案

用户可维护以下结构化偏好：

- 兴趣域和优先级：赛事、电影、本地活动。
- 细分偏好：支持球队、电影类型、活动类型、避开项。
- 约束：单次/周度预算、通勤上限、可用时段、禁止占用的时间、独处/同行偏好。
- 惊喜设置：关闭、低频或每周一次；惊喜计划必须仍满足硬约束。

偏好修改后仅影响后续计划；已进入审批的计划保留其创建时的偏好快照。

### FR-02 创建计划任务

用户可以从首页或对话入口创建任务，系统至少收集：

- 用户的自然语言请求；
- 计划时间范围，默认下一个周末；
- 当前偏好快照；
- 已知日历忙碌时间。

创建成功后应立即显示任务和当前状态，任务状态通过轮询或 WebSocket 推送更新。

### FR-03 候选计划

每次成功规划返回 2–3 个候选方案。每个方案必须包含：

- 标题、活动域、开始/结束时间、地点或“线上”；
- 预计预算、通勤/时长信息；
- 至少一条推荐理由，并区分偏好、实时/插件数据和推断；
- 相关数据来源；
- 将在批准后执行的动作清单。

候选计划不得与已知忙碌时间冲突、不得超过硬性预算、不得违反用户明确避开项。若无合格方案，应返回原因和可调整的条件，而不是编造计划。

### FR-04 审批与执行

以下操作一律需要审批：创建/修改日历事件、创建提醒、保存外部草稿，以及未来所有写操作。

审批卡必须允许用户：

- 查看动作、参数、来源和风险说明；
- 编辑可编辑参数，如标题、时间与提醒时间；
- 批准、拒绝或稍后处理。

批准请求需携带审批版本和幂等键。服务端只接受当前版本的首次批准；重复请求返回同一执行结果，不重复创建事件或提醒。

### FR-05 任务时间线

每个任务显示不可变的关键事件：创建、规划开始、插件查询、规则校验、等待审批、审批结果、执行结果、重试和失败。

每个事件至少记录发生时间、类型、摘要和关联状态。用户可看见推荐依据与执行结果，但不展示模型密钥、原始敏感上下文或内部系统提示词。

### FR-06 插件机制

MVP 插件为 `sports`、`movies`、`calendar` 与 `notifications`。每个插件必须声明：

- capability 名称与输入/输出 Schema；
- 只读或写入副作用等级；
- 所需权限；
- 数据来源与更新时间；
- 审批策略。

AI 只能提出插件调用建议；后端负责 Schema 校验、权限校验、审计和实际执行。

## 5. 非功能需求

### NFR-01 可靠性

- 任务状态的权威副本只存在于后端；客户端本地缓存只用于展示和恢复。
- 任意副作用操作必须具备幂等键。
- 工具调用应具备超时、有限重试和失败原因记录。
- App 重启、网络中断和待审批恢复后，任务不可丢失。

### NFR-02 安全与隐私

- 最小化收集位置、日历和偏好数据；授权范围应可见、可撤销。
- 外部文本和插件数据均视为不可信输入，不能改变审批策略或系统指令。
- 用户的日历、偏好与任务数据只能被对应用户访问。
- 日志和 Trace 不记录密钥、令牌或完整敏感内容。

### NFR-03 可解释性

- 每个候选计划给出清晰推荐理由和数据来源。
- 每个外部副作用都有明确的审批记录。
- 计划不可行时说明冲突、预算或偏好原因。

### NFR-04 性能

- 使用模拟数据时，候选计划在 5 秒内完成。
- 审批后的本地模拟日历/提醒执行结果在 3 秒内返回。
- 客户端收到状态更新后 1 秒内刷新可见状态。

## 6. 三端职责

| 模块 | 必须负责 | 禁止负责 |
| --- | --- | --- |
| `app/` | KMP UI、偏好编辑、任务展示、审批、离线缓存、Android 通知/深链 | 保存权威任务状态、绕过后端执行写操作 |
| `backend/` | Ktor API、状态机、审批版本、权限、幂等、插件执行、审计 | 让模型直接操作日历/通知/数据库 |
| `ai/` | Kotlin Planner、结构化计划提议、理由、Guardrails、评测 | 直接调用有副作用的插件或持久化业务状态 |

## 7. 状态机与验收

任务主路径：

```text
CREATED → PLANNING → GATHERING_CONTEXT → VALIDATING
        → AWAITING_APPROVAL → EXECUTING → COMPLETED
```

`PLANNING`、`GATHERING_CONTEXT`、`VALIDATING` 和 `EXECUTING` 可转入 `RETRYING`、`FAILED` 或 `CANCELLED`。

### MVP 验收标准

- 用户能创建含自然语言约束的周末计划任务。
- 系统基于模拟赛事和电影数据返回至少两个不冲突方案，或返回明确的不可行原因。
- 方案展示预算、时间、理由、来源和待执行动作。
- 未批准前不得创建任何日历事件或提醒。
- 编辑后批准可成功创建一次事件和一次提醒；重复提交不得重复创建。
- 拒绝与失败会显示在同一任务时间线。
- 后端自动化测试覆盖健康检查、状态机关键迁移及幂等审批。
- Android Debug APK 可构建并能展示任务列表、计划详情和审批页的静态/模拟流程。

## 8. 迭代顺序

1. **任务骨架**：任务、状态机、模拟插件、Android 任务列表。
2. **计划与规则**：偏好档案、Planner、候选计划和时间/预算校验。
3. **可控执行**：审批卡、幂等执行、时间线、通知和本地日历模拟。
4. **可靠性**：持久化、重试、离线恢复、Trace。
5. **真实数据与部署**：逐个替换模拟插件，最后容器化部署。

## 9. 主流程详述

### 9.1 首次使用与偏好初始化

**目标**：在不要求用户填写冗长问卷的前提下，获得首次规划所需的最低约束。

```text
启动 App
  → 无偏好档案：进入 3 步轻量引导
  → 选择兴趣与优先级
  → 设置预算、通勤与不可占用时间
  → 可选：授权日历读取、通知
  → 保存偏好并进入首页
```

| 步骤 | App 交互 | 后端行为 | 规则 |
| --- | --- | --- | --- |
| 兴趣选择 | 多选赛事/电影/活动；可长按拖动优先级 | 创建偏好草稿 | 至少选择一个兴趣域，可跳过细分偏好 |
| 现实约束 | 预算输入、通勤滑杆、时间段选择 | 校验并保存结构化约束 | 预算必须大于 0；通勤范围 5–120 分钟 |
| 授权 | “暂不开启”与“去授权”两个同级按钮 | 记录授权状态，不保存系统权限本身 | 没有日历权限仍可规划；只是不读取忙碌时间 |
| 完成 | 显示“先为你生成本周末计划”主按钮 | 创建默认时间范围 | 仅用户点击后才创建任务 |

首次引导不得申请位置、日历、通知以外的权限；每项权限先解释用途，再跳转系统授权。

### 9.2 创建“安排本周末”任务

**入口**：首页主按钮、首页推荐卡、对话页输入框。

```text
用户输入需求
  → App 本地检查必填项
  → POST /tasks，立即获得 taskId 与 CREATED
  → 任务详情显示“正在理解你的安排”
  → 后端依次规划、获取插件数据、规则校验
  → App 收到 AWAITING_APPROVAL，展示候选计划
```

#### 输入框行为

- 占位文案：`例如：周末安排一下，想看利物浦比赛，预算 300，周日下午不要占用。`
- 支持自由文本；下方提供可点选的快捷条件：`本周末`、`独处`、`两人`、`预算 300`、`不要太晚`。
- 快捷条件只负责插入/修改结构化草稿，不直接发起任务。
- 点击“生成计划”后按钮进入加载态且不可重复提交；网络超时后允许重试，重试沿用同一个客户端请求幂等键。
- 若文本为空，提示“告诉 Orbit 你想安排什么，或直接使用默认周末计划”。

#### 后端处理顺序

1. 保存 `Task(status=CREATED)`、请求文本、偏好快照与客户端幂等键。
2. 转为 `PLANNING`，AI 提取软偏好与显式约束；不能从自然语言覆盖档案中的硬限制。
3. 转为 `GATHERING_CONTEXT`，调用只读插件查询赛事、电影、日历忙碌时间。
4. 转为 `VALIDATING`，确定性规则检查时间重叠、预算、通勤、禁用时段和用户避开项。
5. 合格时保存候选计划并转为 `AWAITING_APPROVAL`；无合格项则转为 `COMPLETED`，结果类型为 `NO_FEASIBLE_PLAN`。

### 9.3 候选计划比较与选择

**目标**：让用户在一屏内理解差异并作出选择，避免把模型长文本当成方案。

```text
候选计划页
  → 横向切换 Plan A / B / C
  → 展开查看时间线、理由、来源与待执行动作
  → 选择一个方案
  → 进入审批底部抽屉
```

#### 计划卡固定信息

| 区域 | 内容 | 交互 |
| --- | --- | --- |
| 顶部 | Plan 名称、总时长、预算、线上/线下 | 点击打开详情 |
| 亮点 | 一句话概括，如“主队焦点战 + 步行可达的观赛选择” | 始终可见 |
| 时间轴 | 出发、活动、返程/结束时间 | 点击某段查看来源或约束 |
| 推荐原因 | `符合你的偏好`、`基于活动数据`、`惊喜推荐` 标签化显示 | 点击展开解释 |
| 执行动作 | “将创建 1 个日历事件、1 个提醒” | 点击进入审批 |

#### 比较规则

- 默认按综合匹配度排序；不向用户显示抽象模型分数。
- Plan A 为最匹配方案；Plan B 至少在一个维度有明确取舍，例如更低预算或更少通勤。
- 惊喜方案必须显式标记“新体验”，并说明它满足的既有偏好；绝不伪装成最高匹配方案。
- 用户可以点击“重新生成”，但须选择调整维度：更省钱、更轻松、更多新鲜感或更多赛事优先；该操作创建新任务，不覆盖旧任务。

### 9.4 审批与可编辑执行

**目标**：让用户批准明确的副作用，而不是笼统地批准整段 AI 文本。

```text
点击“安排这个计划”
  → 展开审批抽屉
  → 编辑事件/提醒参数（可选）
  → 批准 或 拒绝 或 稍后处理
  → 批准后：EXECUTING → COMPLETED / FAILED
```

#### 审批抽屉字段

| 字段 | 可编辑性 | 说明 |
| --- | --- | --- |
| 日历事件标题 | 可编辑 | 默认使用计划标题 |
| 开始/结束时间 | 可编辑 | 修改后必须再次通过时间冲突与禁用时段校验 |
| 提醒时间 | 可编辑/可关闭 | 默认赛前或活动前 60 分钟 |
| 日历与通知动作 | 可逐项关闭 | 至少保留一个动作才可批准 |
| 推荐来源 | 只读 | 显示插件名、数据时间和链接 |
| 审批原因 | 只读 | “此操作会创建日历事件/通知提醒” |

#### 审批按钮与反馈

- 主按钮：`批准并安排`；加载中改为 `正在安排…`，禁止再次点击。
- 次按钮：`拒绝`；点击后需选择可选原因：时间不合适、预算过高、不感兴趣、其他。
- 文本操作：`稍后处理`；关闭抽屉但保留 `AWAITING_APPROVAL`，首页待审批数量加一。
- 若审批版本过期，提示“该计划已更新，请重新确认”，拉取最新计划，旧审批不可执行。

### 9.5 执行完成与恢复

**成功状态**：展示已创建的日历事件和提醒、可复制时间安排、`查看任务时间线` 与 `完成`。

**部分成功**：例如日历成功、通知失败。状态为 `COMPLETED_WITH_WARNINGS`（展示层结果，不替换核心状态机），列出成功和失败动作，并提供“重试失败动作”。重试继续使用原动作幂等键。

**失败状态**：保留候选方案和编辑后的审批参数，展示人类可读错误、失败步骤、重试按钮与取消按钮。不得自动把失败任务重新执行超过有限重试次数。

### 9.6 通知与深链恢复

- 出现待审批任务时，若用户开启通知，发送“你的周末计划已准备好，待你确认”。
- 点击通知以 `taskId` 深链打开该任务；若任务已经处理，显示最终状态而非报错。
- 赛前提醒仅在对应审批动作成功后创建。
- App 冷启动、后台恢复和断网恢复时，应拉取未完成任务；本地缓存先显示最近状态，再以服务端状态覆盖。

## 10. 页面与交互规格

### 10.1 页面清单

| 页面 | 目的 | 主操作 | 空状态/异常状态 |
| --- | --- | --- | --- |
| 启动/引导 | 建立最低偏好与权限理解 | 保存偏好、跳过可选项 | 无网络时先保存本地草稿 |
| 首页 | 查看本周、待审批与创建任务 | 创建计划、打开任务、编辑偏好 | 首次用户显示“生成第一个周末计划” |
| 创建任务 | 输入自由需求与快捷约束 | 生成计划 | 校验空输入、重复提交与离线队列 |
| 任务详情 | 观察任务进行、查看候选计划 | 选择方案、重新生成 | 加载骨架、失败重试、无可行方案 |
| 审批抽屉 | 审阅和编辑副作用参数 | 批准、拒绝、稍后 | 版本过期、权限已撤销 |
| 时间线 | 追溯 Agent 决策和执行 | 查看事件详情 | 数据来源失效时保留已记录摘要 |
| 偏好设置 | 编辑长期偏好与授权 | 保存、撤销授权 | 显示上次生效时间 |

### 10.2 首页布局与状态

首页从上到下依次为：

1. 问候与本周日期范围。
2. 待审批横幅：仅在数量大于 0 时显示；点击进入最近待审批任务。
3. “让 Orbit 安排一下”主卡，包含一个单行输入入口和快捷条件。
4. “本周已安排”时间轴，展示已完成计划。
5. “发现的新机会”区域：MVP 仅展示可由用户主动发起的预填充任务卡，不自动执行或自动创建任务。

下拉刷新同步任务、偏好和缓存。离线时顶部显示非阻断提示条，允许浏览缓存和编辑草稿，但“生成计划”“批准并安排”显示为不可用或进入离线队列。

### 10.3 加载、动画与可访问性

- 规划中使用步骤化状态文案：`理解偏好` → `查询活动` → `检查时间与预算`，而不是不透明转圈。
- 状态变更使用短暂淡入，不使用会阻塞审批的长动画。
- 所有图标有 content description；预算、时间和状态不能只通过颜色传达。
- 点击目标最小 48dp；审批按钮固定在底部安全区域上方。
- 所有日期和时间按设备时区格式化；后端保存 UTC 与用户时区。

## 11. 异常与边界交互

| 情况 | 用户看到的行为 | 系统行为 |
| --- | --- | --- |
| 无日历权限 | “未读取你的已有安排，可能产生冲突” | 允许继续；审批前再次提示 |
| 日历权限被撤销 | 审批按钮禁用并提供“重新授权” | 不执行日历动作；保留任务 |
| 无可行计划 | 显示冲突原因与快捷调整项 | 完成任务，不虚构候选项 |
| 插件数据过期 | 标注“数据可能已过期” | 不自动执行涉及过期数据的写操作 |
| 网络中断 | 显示缓存；创建/审批可保留为草稿 | 使用幂等键，恢复网络后重新同步 |
| 并发审批 | 显示“已在其他设备处理” | 服务端基于审批版本拒绝过期请求 |
| 用户删除计划 | 二次确认“仅取消 Orbit 任务，还是同时删除已创建日历事件？” | 两类动作分别审计；日历删除需新审批 |

## 12. 接口与数据最小契约

### 12.1 初始 API

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/v1/tasks` | 创建计划任务；请求携带客户端幂等键 |
| `GET` | `/v1/tasks/{taskId}` | 获取任务、候选计划、审批和时间线 |
| `GET` | `/v1/tasks/{taskId}/events` | 获取状态事件；后续可升级为 WebSocket/SSE |
| `POST` | `/v1/tasks/{taskId}/approvals/{approvalId}` | 批准、拒绝或稍后；携带审批版本 |
| `GET/PUT` | `/v1/preferences/me` | 读取和更新偏好档案 |
| `GET` | `/v1/health` | 健康检查 |

### 12.2 任务最小字段

```text
Task
- id, userId, status, resultType, requestText
- preferenceSnapshot, timeRange, createdAt, updatedAt
- planOptions[], approvals[], timelineEvents[]

Approval
- id, taskId, version, status, actionType
- editablePayload, idempotencyKey, decidedAt

TimelineEvent
- id, taskId, type, occurredAt, summary, metadata
```

`preferenceSnapshot`、`editablePayload` 和插件调用参数均需版本化，避免以后字段演变造成旧任务无法恢复。
