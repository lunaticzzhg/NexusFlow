# 核心原则结论门禁

## 目标与范围

本门禁防止开发或 review 只声称“已检查”而没有可追溯结论。它适用于 Orbit 的有意义开发切片和完整代码审查；不替代各专题的架构、合同或验证规则，也不要求为未命中领域填写表格。

## 结论规则

先选择本次实际命中的原则。每个命中项必须给出 `通过`、`不通过`、`不适用` 或 `未验证` 之一：

- `通过`：给出最小代码、测试或命令证据。
- `不通过`：在 review 中报告 P0–P2；在开发中修复或明确交由完整 review 处理。
- `不适用`：说明该原则为什么未命中。
- `未验证`：说明缺口、残余风险和需要的验证。

不得以“架构合理”“已检查”或“测试通过”替代结论。任何命中项没有结论时，切片验收或 review 不完整。

## 核心原则

以下原则始终优先于命名、目录和抽象偏好；命中时必须给出结论：

| 原则 | 命中信号 | 最小证据 |
| --- | --- | --- |
| 状态机与重复操作 | ViewModel、多阶段流程、加载、刷新、分页、提交 | 状态是否排除非法组合；重复操作的行为；命中[复杂流程状态机规范](state-machines.md)时提供状态集合、迁移表、唯一 owner、操作身份、清理责任与转换测试 |
| 数据归属与上下文失效 | user/tenant/task、缓存、导航、异步请求 | scope/key、失效范围、迟到结果 |
| 合同字段可达性与兼容性 | DTO、domain、API、列表或详情 | 字段从输入到 UI、导航或行为的消费点；缺失字段默认行为 |
| 失败、取消与迟到结果 | coroutine、Job、重试、外部调用、缓存写入 | owner、失败可见性、取消与旧结果拦截 |
| 用户可见降级 | 异步 UI、loading、empty、error、retry | 内容保留、错误/空态区分、可恢复入口 |
| 验证证据 | 所有有意义改动 | 已运行命令、测试范围与未覆盖原因 |

条件原则只在对应主题命中后进入结论卡：分层与依赖方向、common/platform 边界、协程调度、安全与隐私、本地化与无障碍、UI 渲染、性能与资源、DI 生命周期。

## 必须对照的模式

- 命中列表、缓存、刷新或分页时，读取 `list-data-lifecycle.md` 和 `loading-feedback.md`，并对照一个同仓成熟实现。单列表具有本地首屏缓存、显式刷新或真实分页时，必须说明为什么使用或不使用 `ListLoadPhase`；未完成对照不得判定状态设计通过。
- 命中 DTO、domain 或详情页时，检查每个有业务语义的字段是否最终驱动 UI、导航或行为。没有消费点时，明确分类为缺失能力、风险或 defect；不得默认忽略。

## 升级到完整 Review 的条件

开发切片默认只完成本门禁。出现任一条件，或用户明确要求 review 时，再执行 `code-review-and-refactoring` 的完整流程：

- API、DTO、认证、权限、隐私或兼容性；
- user/tenant scope、缓存、并发、取消、重试或后台任务；
- 平台能力、DI 生命周期或跨 feature 边界；
- 大型重构、职责拆分或抽象选型；
- 开发自检无法判断状态机、资源所有权或失败行为。

## 输出

将结论卡并入已有的薄切片记录或 review 报告，不创建独立流程文档：

```md
| 命中原则 | 结论 | 证据或缺口 |
| --- | --- | --- |
| 状态机与重复操作 | 通过 | ListLoadPhase；首屏/刷新/分页测试 |
| 合同字段可达性 | 不通过 | `content` 没有 UI 消费点 |
| 验证证据 | 未验证 | 未进行模拟器验收 |
```

## 非目标

本门禁不要求每次执行完整 code review、不把未命中专题变成必填项，也不替代具体专题中的实现与测试规则。
