# 规范治理

规范是可执行的长期决策，不是一次讨论、实现细节备忘或个人偏好集合。目标是在提升重复决策效率的同时，避免规则膨胀、重复与冲突。

## 何时沉淀

仅在下列任一条件成立时新增或修改规范：

- 同一判断已在多个需求或 review 中重复出现；
- 已发生的缺陷、平台限制、安全要求或产品约束需要防止再次发生；
- 新增基础能力、跨端边界或生命周期契约，且后续调用者必须遵守；
- 现有规则存在冲突、遗漏或已被事实证明不再适用。

一次性的实现选择、未经验证的猜测、低概率且没有明确收益的极端 case 不沉淀为规范；在需求记录或 review 中保留其上下文和重新评估信号即可。

## 写入位置与唯一事实来源

先确定规则的稳定归属，只在一个位置写完整细则：

| 规则类型 | 唯一事实来源 | 其他位置的职责 |
| --- | --- | --- |
| 全局强制原则、入口与路由 | `AGENTS.md` | 仅链接到细则。 |
| 开发或 review 的步骤、触发条件 | 对应 Skill 的 `SKILL.md` | 仅引用专题规则。 |
| 跨 feature 架构、平台能力、生命周期、契约 | `docs/architecture/` 或对应 Skill `references/` | 选择已有专题；没有稳定专题才新建。 |
| 需求的暂时性方案、取舍、非目标与风险 | 需求记录或 review 结论 | 不升级为长期规范。 |

新规则先搜索现有规范和相邻能力。能扩展既有专题时不得新增平行文档；只有独立主题会被重复查阅、拥有明确边界且无法放入现有专题时，才新建文档。入口、Skill 与总则可以提供简短路由，但不得复制完整细则。

## 最小规则模板

每条长期规则必须能回答：

1. **触发与目标**：解决什么重复决策、真实风险或边界？
2. **适用范围与非目标**：何时必须遵守，何时不适用？
3. **职责与边界**：谁拥有行为、状态和平台互操作？
4. **明确动作**：开发者应做什么、不应做什么；必要时给正反例。
5. **验证与例外**：如何证明遵守；例外需要什么事实依据、记录什么差异？

规则应使用稳定的领域语言，避免以当前某个 feature、临时类名或文件路径替代抽象边界。只有当具体实现本身就是固定契约时，才记录其名称。

## 变更流程

1. 说明触发证据、目标和非目标，先检查是否能以更小的局部改动解决。
2. 搜索所有可能的既有来源，确定唯一事实来源与受影响路由。
3. 以最小规则模板写入；冲突时先删除或改写旧表述，不保留相互矛盾的“例外”。
4. 只更新实际需要的入口、Skill 或专题链接；不为可见性复制内容。
5. 核对术语、链接、交叉引用和相邻规则的一致性；执行 `git diff --check`。涉及代码或构建规则时，再运行对应最小验证。
6. 交付时说明新增或调整的规则、唯一事实来源、替代的旧表述与未处理的风险。

## 质量门槛

- 规则必须能改善业务逻辑正确性、业务架构层次，或降低重复决策成本；否则不加入。
- 规则应与 ROI 一致：优先规范高频、高影响或已发生的问题，不把架构偏好包装成强制流程。
- 不得以规范要求预设抽象、模块、Factory、注册表或平台分叉；规则只约束已证实的边界与行为。
- 外部平台、库或版本敏感事实必须有官方资料或当前工程证据，并注明需要重新核验的条件。

## 需求依赖的基础设施

当一个已确认需求的正确交付依赖尚未具备的基础设施时，基础设施属于该需求的首个实现切片，不能以“后续再接入”为由长期用 Mock、内存实现或人工步骤替代。

### 适用范围与非目标

- 适用于需求已经明确需要持久化、认证与密钥管理、第三方平台配置、消息/事件基础设施、平台能力宿主或其他运行前提，但当前工程尚未提供该能力的情况。
- 不要求为推测中的未来需求预建基础设施；只有当前需求的正确性、可靠性、安全性或可验证性依赖它时才引入。
- 一次性的纯 UI 演示、明确标注为原型的代码，以及已有权威基础设施的普通接线不适用。

### 方案与实施顺序

方案必须先列出缺失的基础设施、其 owner、配置/密钥边界、运行环境、验证方式和业务代码对它的依赖。实施按以下顺序进行：

1. 建立当前需求所需的最小基础设施及可重复的本地/测试环境；秘密仅通过环境或 Secret 管理注入。
2. 建立基础设施的最小可验证契约、健康检查或集成验证；持久化结构从首次建表起使用版本化脚本。
3. 在该真实基础设施上实现业务 API、Repository、平台适配或 UI 流程。
4. 以端到端或跨边界验证证明业务代码使用真实能力；Mock 只保留给可控测试场景，不充当长期运行路径。

不得把基础设施缺失当作延后正确性边界的理由，例如让客户端伪造服务端状态、在生产路径保存明文凭据、用内存会话替代需要持久化的会话，或绕过应有的认证与权限验证。

### 例外与验证

若暂不引入基础设施，方案必须说明该需求为何仍能正确交付、替代实现的明确生命周期，以及触发切换到真实基础设施的条件。验证至少覆盖基础设施可启动/可连接、配置缺失时的失败行为、秘密不进入源码或日志，以及业务切片确实通过该基础设施运行。
