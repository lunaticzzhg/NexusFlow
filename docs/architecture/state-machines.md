# 复杂流程状态机规范

## 目标与触发证据

本规范用于避免以 `Job?`、多个 Boolean、可空进度值或回调时序共同推导一个复杂业务流程的阶段。它适用于已经发生或可信会发生的状态错配、重复操作、迟到结果、取消清理或上下文切换问题；不要求为普通请求建立状态机框架。

当同一流程命中下列任意两项时，必须在编码前给出显式状态机：

- 至少三个用户可见阶段，或阶段之间有不同文案、可用操作或完成条件；
- 外部或平台 I/O、异步回调、后台 worker、队列或订阅；
- 用户取消、重试、跳过、确认或重复触发；
- 临时资源、持久化提交点或必须完成的清理；
- 用户、租户、会话或导航生命周期会使运行中的工作失效；
- 迟到结果、并发请求或旧 callback 可能回写当前可见状态。

简单的单次请求仍可使用紧凑的 `Idle/Loading/Content/Error` UI 状态，不必为了形式创建 session、协调器或新 module。只有业务需要独立的操作身份、取消语义或资源生命周期时，才建立 operation/session 对象。

## 唯一事实与边界

- 一个复杂流程必须有唯一的状态 owner。UI 观察状态并派发意图，不自行拼接后台 Job、资源或回调的生命周期。
- 业务状态、迁移、取消、重试、资源清理和失败分类位于 `commonMain`；平台 source set 仅实现原子 I/O 或系统 callback，并返回结构化结果。
- Job、mutex、request token、cursor 和平台句柄是协调细节，不是可渲染业务状态。它们可由 owner 私有持有，但不能让 UI 通过它们与多个字段推导阶段。
- 当操作的有效性依赖用户、租户或会话时，owner 在启动时捕获该身份；身份失效时必须定义取消、等待清理和拒绝旧结果的顺序。取消只是资源优化，不能是阻止旧结果写回的唯一正确性保证。

## 建模要求

状态优先使用 `sealed interface` 或同等穷尽模型。每个状态只保存该阶段可渲染、可恢复或决定后续迁移的事实。

状态机设计必须在方案中给出：

1. 状态集合和终态；
2. 事件集合；
3. 迁移表；
4. owner、操作身份和上下文身份；
5. 外部副作用、提交点和清理责任；
6. 用户可见反馈与验证用例。

最小迁移表示例：

| 当前状态 | 事件 | 下个状态 | 必须完成的副作用 |
| --- | --- | --- | --- |
| `Running` | 用户取消 | `Cancelling` | 阻止启动后续工作 |
| `Running` | 当前项完成 | `Running` 或 `Completed` | 记录结果、推进进度 |
| `Cancelling` | 当前项到达安全点 | `Cancelled` | 清理未提交资源 |
| `Running` | 不可恢复失败 | `Interrupted` | 保留安全的已提交结果、清理其余资源 |

未列出的事件默认不得改变状态。终态不得再接受进度、成功或失败回调；新操作必须使用新的操作身份。

## 进度、提交与清理

- 进度必须表达真实含义。`currentItem`（正在处理第几个）与 `completedCount`（已完成几个）不得混用；百分比只从已完成的工作推导，不能在最后一项开始时提前显示 100%。
- 进度事件必须携带或绑定操作身份；owner 只接受当前身份且满足单调性/阶段约束的事件。
- 每个有持久化或入队行为的流程必须定义提交点。提交点之前取消可删除临时结果；提交点之后保留已提交事实，并只停止后续工作。
- 取消、失败和上下文失效的清理必须由拥有资源路径的层执行，并在必要时使用不可取消区保证删除与句柄释放。调用者不得猜测或分别拼接临时/正式资源路径。
- 清理失败不得静默吞掉：它必须以结构化诊断记录，并保留可恢复的孤儿清理路径。

## UI 与交互

- 每个可见状态必须定义允许的用户操作、禁用操作、离开/关闭规则和反馈文案。
- 用户发出取消后，UI 必须先同步进入可见的 `Cancelling` 状态，再等待平台工作到达安全点；不能只调用 `Job.cancel()` 而保持原界面。
- UI 是否显示流程表面必须由同一状态机决定，不能与另一个 `Job?`、Boolean 或回调字段分别控制。
- 后台任务的结果与前台流程的结果应分层表达。例如“任务已接受”不等于“方案已生成”或“审批动作已执行”；重复事件、计划失败等后台结果不能静默抹除用户可见任务。

## 验证

每个命中本规范的流程至少覆盖与其实际能力对应的转换：

| 场景 | 最小断言 |
| --- | --- |
| 正常完成 | 状态单调进入终态；终态后无进度回写 |
| 重复触发 | 明确拒绝、合并或替换，不产生第二个 owner |
| 取消前、处理中、提交点后 | 用户可见状态、保留事实与清理范围符合契约 |
| 失败 | 失败可见；安全的已提交结果不丢失 |
| 迟到结果 | 旧 operation/context 的事件不能覆盖当前状态 |
| 上下文失效 | 先停止/清理旧工作，再关闭依赖资源 |
| 平台限制 | 取消响应点和资源释放在受影响 target 上验证或明确记录未验证原因 |

测试应优先断言状态和可观察副作用，而不是私有 Job 或实现顺序。涉及平台 I/O 的共享状态机需要 `commonTest` 覆盖迁移，并补最小平台验证。

## 非目标

- 不引入通用状态机框架、事件总线、注册表或全局 session 管理器。
- 不要求把简单 loading/error 请求拆成大量状态或文件。
- 不替代 `context-runtime.md`、`coroutine-dispatching.md`、平台能力或网络契约；命中这些边界时仍须同时遵守对应规范。
